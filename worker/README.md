# busnavi リアルタイムAPIの反映

全利用者のアクセスを一つの Durable Object に集約する版です。
以前渡した「コードを貼るだけ」の版と異なり、共有保存先の設定も必要です。
このフォルダの設定ファイルで、コードと保存先を一緒に反映できます。初回の公開は完了しています。以後の更新にも同じ手順を使えます。

## 反映手順（Macのターミナル）

以下を実行します。ログイン画面が開いたら、既存の `busnavi-realtime` を作ったCloudflareアカウントで承認してください。

```sh
cd busnavi/worker
npm ci
npx wrangler login
npm run deploy
```

`npm ci` はツールの準備です。初回は準備済みなので省略できます。
`wrangler.jsonc` には既存と同じ Worker 名 `busnavi-realtime` を指定しています。
複数アカウントが表示された場合は、既存Workerのアカウントを選んでください。
`worker.js` だけを管理画面に貼り付けても、保存先との接続設定がないと動作しません。

反映後は次を開きます。
https://busnavi-realtime.rnp9cf8k76.workers.dev/api/realtime

`version: 2`、`intervalSeconds: 30`、`feeds`（4社）が出ていれば新しい版です。
各社の `ok: true` と `timestamp` が現在に近いことも確認します。
ローカル画面 http://127.0.0.1:8001/ を再読み込みすると、自動接続します。
GitHub Pagesの公開画面を変更するには、別途フロント側の更新を公開する必要があります。

## 取得仕様

- 4社それぞれへの取得は、全利用者合計で最短30秒間隔。
- 同時アクセスも一つの取得にまとめます。URL末尾の変更で取得制限を回避できません。
- 間隔は取得開始前に永続保存。再起動時や取得失敗時にも、短時間の再取得を防ぎます。
- 閲覧者がいなければ取得しません。30秒経過後の次のアクセスで更新します。
- 拠点ごとのキャッシュや定期実行は使いません。
- ブラウザは表示中のみ30秒ごとに確認。タブ非表示・指定日時モードでは停止します。
- `generatedAt` はAPI側の集約時刻、各社 `timestamp` は配信元の更新時刻です。
- APIは古い保存内容を返す場合もありますが、画面は更新から90秒超の予測を使用しません。取得できない情報を定刻扱いしません。
- 運休・停車取りやめを取得できた便は案内対象から除きます。未取得の運休は判定できません。
- 実際の予測を取得できた出発・到着だけを「予測」とし、その他は「予定」と明記します。下車停留所の発車予測を到着予測に読み替えません。
- 静的GTFSとtrip_id・運行日・停留所・停車順序を照合。曖昧な便の予測は採用しません。追加便・臨時便の新規生成や遅延の推測伝播は行いません。

## 検証

親フォルダで `npm test`：取得集約・30秒制限・再起動・エラー時・CORS・遅延時の並び順・運休・情報の古さ・非表示時停止を検証します。
このフォルダで `npx wrangler deploy --dry-run`：Cloudflare用設定・コードを検証できます。

配信元：https://www.bus-kyo.or.jp/gtfs-open-data （CC0）
Cloudflare公式：https://developers.cloudflare.com/durable-objects/get-started/

## 初回反映後の更新

上流の `.bin` にCloudflareの中間キャッシュが残らないよう、取得時に `cache: 'no-store'` を指定しました。更新には同じフォルダで `npm run deploy` を実行します。ログイン済みならログイン操作のやり直しは不要です。反映後、最長30秒程度で新しい取得に切り替わります。各社 `timestamp` が進むことを確認してください。
